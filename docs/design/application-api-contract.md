# Минимальный контракт API учебных модулей — проект Д0

**Статус:** проект для обсуждения, 27.10.2026. API, JSON CLI и приведённые сценарии не реализованы и не тестировались. Имена, значения и версии ниже — предлагаемые, не утверждённые публичные идентификаторы. Основания: [архитектура](application-architecture.md), [методическое взаимодействие и M01–M10](methodical-interaction.md), [сценарий теплообменника](heat-exchanger-learning-flow.md), [портфель](laboratory-portfolio.md), [план](../CODEX-PLAN.md), [открытые вопросы](../OPEN-QUESTIONS.md). Пример R04 — [математический эталон](heat-exchanger-reference-cases.md) идеальной модели с заданным UA, не экспериментальная валидация.

## 1. Границы

Общий слой предоставляет поиск модуля и материалов, оболочку сеанса, передачу команд, диагностики, сохранение и транспорт. Предметный модуль определяет содержание состояния, доступные действия, правила применимости, собственные типы результатов, их зависимости и допустимые источники. Модуль может быть установкой, диаграммой, расчётным исследованием или качественной схемой. Не требуется общий суперкласс оборудования, насосы, приборы, часы, этапы, результаты-числа или автоматическая оценка. Наличие справки и записи ответа не обязывает модуль создавать задания или выполнять проверку.

Один семантический контракт должен быть доступен напрямую из чистого Python и через JSON CLI, далее — через Python–JS мост. Ни GUI, ни адаптер CLI не определяют физические данные, допустимость или проверку; они лишь передают запрос и отображают результат. Ниже `op` — концептуальные операции, не окончательные Python-имена. Общий диспетчер передаёт `action` конкретному модулю, не знает, что такое `UA`, поток, точка или теплообмен.

## 2. Операции

Во всех строках поля, помеченные `*`, обязательны при данном варианте. Поля конкретного действия определяет модуль; имя операции не означает обязательность оборудования или наличия результата.

| Операция | Полезная нагрузка запроса | Успешный результат `data` | Ответственность |
|---|---|---|---|
| `module.info` | `module_id*` | ID, название, виды интерактивности, версия модуля, статус модели, допустимые возможности | Общий каталог + метаданные модуля |
| `session.create` | `module_id*`, необязательный `options` | `session_id`, начальная `revision`, модель и состояние | Модуль создаёт содержимое, общий слой выдаёт ID |
| `session.restore` | `document*` — ранее сохранённый документ | `session_id`, восстановленная `revision`, состояние, статус модели | Хранилище проверяет формат; модуль проверяет и восстанавливает свою версию |
| `session.state` | `session_id*` | `revision`, текущее состояние, ссылки на черновики и снимки, состояние модели | Модуль; отсутствие снимков допустимо |
| `session.actions` | `session_id*` | Действия с `action`, `available` и причиной недоступности | Модуль; список зависит от состояния |
| `session.command` | `session_id*`, `expected_revision*`, `action*`, `params*` — объект | Новая `revision`, результат действия и изменённые данные либо диагностика | Модуль: предметное действие, включая изменение условий, выбор точки, расчёт, фиксацию снимка и ввод черновика |
| `session.results` | `session_id*`; необязательные `snapshot_id`, `result_id` | Список результатов, их связи, статусы и диагностики | Модуль; публичная выдача подчиняется политике задания |
| `material.get` | `material_id*`; необязательные `session_id`, контекст | Материал с ID, видом, текстом и источником/условиями при наличии | Общий каталог; контекст и право доступа определяются модулем/правилами |
| `answer.put` | `session_id*`, `expected_revision*`, `task_id*`, `context_ref*`, `value*` | ID ответа, новая ревизия, ответ и статус `not_checked` | Общее хранение формы; допустимые типы и смысл — модуль |
| `answer.check` | `session_id*`, `expected_revision*`, `answer_id*` | Новая ревизия и проверка с применимым контекстом и статусом | Модуль использует только утверждённые для задания эталон, метод и допуск; иначе `not_checked` |
| `session.save` | `session_id*`, `expected_revision*` | `document`, сохранённая ревизия | Общий сериализатор; модуль возвращает свой полезный груз |
| `storage.write` | `document*`, `target*` — пользовательское назначение | Подтверждение записи, идентификатор/путь и сохранённая ревизия | Общий слой хранения; только успешная атомарная запись считается сохранением |
| `storage.read` | `target*` | Считанный `document` либо диагностика | Общий слой; содержимое и совместимость окончательно проверяются при restore |
| `session.export` | `session_id*`, `expected_revision*` | Переносимый `document` выбранного поддерживаемого формата | Общая оболочка + сериализация модуля; затем `storage.write` |

`session.restore` используется и после `storage.read`, и после импорта переносимого документа. `target` относится к хранилищу, а не предметному модулю; реализацию путей и политику доступа ещё согласовать. `session.save` подготавливает документ, но **не** утверждает успешную запись. `session.export` не означает автоматический импорт или запись. `material.get` возвращает разрешённый собственный материал по стабильному ID, а не содержимое чужого PDF; права — Q11.

Примеры действий модулей: `set_conditions`, `calculate_ideal`, `capture_snapshot`, `get_stand_readings`; `select_region`, `save_draft`, `get_properties`, `construct_process`. Общий API не навязывает эти действия и не интерпретирует их параметры. Действие, указанное как недоступное, всё равно может быть запрошено: модуль обязан вернуть ту же объяснимую диагностику без изменения состояния.

## 3. Запросы, ответы и типы

### Оболочка

Запрос: `api_version*` — версия контракта (`"0.1"` в примерах), `request_id*` — непрозрачный ID для сопоставления, `op*`, `args*` — объект; идентификаторы сеанса и ожидаемая ревизия находятся в `args`, если указаны в таблице. Ответ: `api_version*`, `request_id*`, `outcome*` (`ok` или `error`), `data*` (объект для успеха, `null` для отказа), `diagnostics*` (массив, допускается пустой). `ok` означает, что операция выполнена: это не подтверждение физики или ответа студента. `not_checked` может быть успешным ответом операции проверки. Для `error` минимум одна диагностика, частичные предметные изменения не допускаются. Неизвестные операции, версии и обязательные поля дают диагностику; поведение дополнительных полей ещё согласовать.

Состояние модели — отдельная информация по областям/возможностям, а не одно глобальное «модель готова». Минимум: `capability`, `availability` (`available`, `unavailable`, `unknown`), `basis` — ссылка на источник/версию, если есть. Доступность условной ε–NTU не делает доступными показания конкретного стенда; модель диаграммы может быть недоступна при доступном качественном выборе.

### Значения

| Тип `kind` | Обязательные поля содержимого | Необязательные поля и смысл |
|---|---|---|
| `quantity` | `value`: конечное число; `unit`: стабильный ID единицы для размерной величины; `quantity_id` | `entered` с исходными числом и единицей, если выполнено преобразование; безразмерное число использует `unit: "1"`. Недопустимы NaN/Infinity |
| `object_selection` | `object_id` | Роль/описание из модуля; единица не требуется |
| `diagram_point` | `point_id`, `representation` (`qualitative` или `physical`) | Для качественной точки — `region_id` или иной модульный контекст без физических координат; для физической — типизированные координаты и условия, включая давление, если требуются. Нельзя интерпретировать экранные координаты как свойства |
| `series` | `series_id`, `items` — упорядоченный массив | Элементы типизированы модулем, включая единицы и, если есть, источник; пустой массив допустим для черновика |
| `student_answer` | `task_id`, `context_ref`, `value` — типизированное значение или текст | `answer_id`, проверка и ревизия; ответ студента не является результатом модели |
| `material_ref` | `material_id` | Место в источнике и версия материала, если имеются; не копия первоисточника |
| `text` | `value` | Для собственного вывода; физическая правильность не проверяется без критерия |

Для размерной величины модуль или каталог объявляет допустимую размерность и единицы. Известные совместимые единицы преобразуются с сохранением ввода и нормализованного значения; несовместимая/неизвестная единица возвращает диагностику с полем, ожидаемой размерностью и разрешёнными единицами. Допустимые температуры, границы, округление, погрешность и точное обозначение единиц определяются отдельной спецификацией; для температуры различать абсолютные значения и разности. Качественное значение единицы не имеет.

### Результат и независимые статусы

Каждый выдаваемый результат имеет `result_id*`, `value*` типизированного вида, `provenance*`, `data_state*`, `context_ref*`; `model_ref`, `assumptions`, `verification` и источники необязательны по смыслу. `context_ref` связывает результат с версией сеанса или неизменяемым снимком, например `{"snapshot_id":"hx-s1"}`. Пример содержимого:

```json
{"result_id":"heat_rate","value":{"kind":"quantity","quantity_id":"heat_rate","value":30000,"unit":"W"},"provenance":{"kind":"ideal_model","source_id":"hx-r04","model_version":"ideal-demo-1"},"data_state":"current","context_ref":{"snapshot_id":"hx-s1"},"assumptions":["steady","constant_capacity_rates","known_UA","no_losses"]}
```

- **`provenance.kind`**: `user_entered`, `provided_dataset`, `ideal_model`, `validated_model` или `unknown`; для внешнего источника/модели при наличии `source_id`, версия и ограничения. Неизвестный источник не объявляется подтверждённым.
- **`data_state`**: `draft`, `current`, `frozen`, `stale`, `unavailable` в зависимости от вида объекта. Замороженный снимок остаётся действительным для своего контекста; ссылка на него как на ответ для изменённых текущих условий устаревает. `unavailable` обычно передаётся диагностикой без фиктивного значения.
- **Проверка студенческого ответа**: `not_checked`, `matches`, `does_not_match`; при проверке дополнительно `method_id`, `reference_id`, `reference_version`, `tolerance` и `context_ref`. Статус отражает только ответ в данном контексте и не является оценкой всей работы. Если применимость не установлена, эталон/метод/допуск не утверждён или контекст устарел — `not_checked` с причиной; доказанная неприменимость и плохой ввод — диагностика отказа.
- **Доступность модели** хранится отдельно по возможностям, как выше. Ошибка формата, физический предел, неустановленная применимость, отсутствие модели и ошибка записи — разные диагностики, а не один `valid`.

### Диагностика

Объект `code*` (стабильный машинный код), `category*` (`input`, `applicability`, `availability`, `conflict`, `storage`, `compatibility`), `message*` (русский текст), `severity*` (`error` или `warning`), необязательные `field`, `expected`, `actual`, `hint`, `material_id`, `details`. `hint` предлагает проверяемое действие, не раскрывает правильное решение; `details` не содержит скрытых эталонных ответов или локальных чужих материалов. Локализация текста не меняет `code`. Для неопределённой причины не заявлять точно, какое действие было ошибкой.

Пример несовместимой единицы:

```json
{"code":"unit.incompatible","category":"input","severity":"error","message":"Единица не соответствует температуре.","field":"params.hot_in.unit","expected":{"dimension":"temperature","units":["degC"]},"actual":"kg","hint":"Выберите единицу температуры."}
```

## 4. Версии, состояние и хранение

`revision` — монотонное целое версии текущего содержимого сеанса; первоначально 0. Мутация (`session.command`, `answer.put`, `answer.check`) требует `expected_revision` и при успехе увеличивает её на 1; чтение, справка, сохранение документа и запись не меняют ревизию. При конфликте возвращается `revision.conflict` с фактической ревизией, без изменения данных; клиент повторно читает состояние и осознанно применяет изменение. При отказе мутации ревизия и ранее сохранённые данные не меняются. Если проверка уже имеет результат, повтор всё равно является отдельной успешной мутацией или модуль может предложить не выполнять её; точная политика идемпотентности — открытый вопрос.

Черновик хранит незавершённый ввод, включая нечисловой текст и единицу: команда сохранения черновика отличается от команды применения проверенного параметра. Невалидный прикладной параметр отклоняется, но уже сохранённый черновик сохраняется. `snapshot_id` обозначает неизменяемое содержимое с `snapshot_version`, источниками и зависимостями; редактирование создаёт новую ревизию/снимок. Отмена вычисления, отказ, справка или закрытие приложения не переписывают старый снимок. Производные результаты ссылаются на конкретные снимки/версии; для новых входов прошлые ответы не выдаются как актуальные. Пересчёт — явное действие при наличии оснований.

Предлагаемый файл сеанса — JSON-объект:

```json
{"format":"food-processes-session","format_version":1,"module_id":"humid-air","module_version":"0.1","session_id":"air-1","revision":1,"module_data_version":1,"module_data":{"selection":{"kind":"diagram_point","point_id":"p1","representation":"qualitative","region_id":"schematic-area-a"},"drafts":{},"snapshots":[]}}
```

Обязательны все поля примера; `module_data` — непрозрачный для общего хранилища JSON-объект, сохраняется целиком, включая черновики, ссылки, историю и проверки; набор ключей выбирает модуль. Теплообменник может хранить в нём входы и снимки, диаграмма — точки и линии без общей физической схемы. При восстановлении общий слой проверяет конверт и формат, затем соответствующий модуль проверяет собственную версию/целостность и восстанавливает ссылки. Неизвестный модуль, неподдерживаемая версия, отсутствующая миграция или повреждение — явный отказ без перезаписи исходного документа; миграция только при известном правиле. Подтверждение записи относится к конкретной ревизии: изменения после неё остаются несохранёнными.

Файл пользователя хранится вне EXE; запись в тот же каталог через временный файл с последующей заменой, ошибки и сохранение предыдущей успешной версии подлежат будущей проверке на целевой Windows. Детали восстановления после внезапного сбоя и гарантии файловой системы остаются Q16; нельзя обещать сохранность неуспешно записанного черновика после аварии. Для первого среза достаточно файла, база данных не обоснована. Форматы пользовательского экспорта, переносимости и разрешённые места хранения остаются Q15/Q16.

## 5. Примеры обмена: условный теплообменник

Далее каждая строка — самостоятельный JSON-объект запроса или ответа; идентификаторы условны. Они демонстрируют полный обмен, не факт выполнения. Условная демонстрация явно разрешает показать результат расчёта; в задании со скрытым ответом политика выдачи и авторизация иные. Версия модели и источник в примере — предлагаемые ID; реальный модуль и право раскрытия результата ещё не утверждены.

## 7. Методические сценарии M01–M10

| ID | Операции и проверяемая гарантия |
|---|---|
| M01 | `session.create` → `set_conditions` → `capture_snapshot` → `answer.put` → `answer.check`: R04, `matches` только для отдельного тестового задания с утверждёнными эталоном/допуском; при их отсутствии `not_checked`. Демонстрационный `calculate_ideal` не раскрывает решение скрытого задания. |
| M02 | `save_draft` сохраняет сырую строку; применение параметра через `session.command` возвращает `input.invalid_number`/`input.required`, прежний снимок и черновик не пропадают. |
| M03 | `session.command` с kg вместо температуры → `unit.incompatible`, поле и допустимая размерность; при известном преобразовании сохранить ввод и нормализованное значение. |
| M04 | Достоверно неприменимая ε–NTU при нулевом C → `applicability.invalid_capacity`; неизвестная область при `answer.check` → `not_checked` с причиной. Ни `NaN`, ни вымышленного ответа. |
| M05 | `capture_snapshot` A → `session.save`/`storage.write` → изменение в новой ревизии → `storage.read`/`session.restore` после последующего успешного сохранения: A неизменен, зависимый результат для новых данных устарел; ревизии и ссылки сохраняются. |
| M06 | `session.actions` показывает недоступность показаний, `get_stand_readings` отказывает с `model.stand_unavailable`; черновики и справка доступны. |
| M07 | Сохранить черновой ввод, `material.get` по ID элемента/формулы, снова `session.state`: черновик и ревизия не изменились; формула и ограничения без автоматической выдачи решения. |
| M08 | `select_region`, затем `get_properties`/`construct_process`: качественный черновик сохраняется, физические значения недоступны; `answer.check` возвращает `not_checked` при отсутствии основания. |
| M09 | Два `capture_snapshot`, модульная команда сравнения возвращает отличия входов, происхождение и контексты; отдельный `answer.put` сохраняет собственный вывод без автоматической оценки. |
| M10 | `session.save` → намеренный отказ `storage.write`: диагностика `storage.write_failed`, текущий черновик остаётся в памяти, предыдущая запись не считается заменённой; после аварии гарантируется только реально успешная запись. |

## 8. Инварианты и критерии будущей проверки

1. У каждого `request_id` ответ с тем же ID; ошибка не является частичным успехом и не изменяет подтверждённые данные. Несовпадение ревизии не перезаписывает чужое изменение.
2. Снимок неизменяем, изменение условий создаёт новую ревизию/снимок; проверка ответа и результат связаны с конкретной версией, новые условия не наследуют старую проверку.
3. Происхождение, состояние, проверка, наличие модели и диагностики представлены раздельно. `ok` и факт сохранения не означают валидности физики.
4. У чисел конечные значения и однозначные единицы; качественные данные не требуют единицы, физические координаты точки не выводятся из экранных без подтверждённой модели. Нельзя выдавать `NaN` и Infinity.
5. Справка и чтение не меняют предметную ревизию; черновики не теряются от ошибки, успешный save не подтверждает запись до `storage.write`.
6. Результат проверки ограничен утверждёнными эталоном, методом, допуском, условиями и их версиями; иначе `not_checked`. Скрытый ответ не выдаётся через справку, `session.state`, `session.results`, сохранение и экспорт задания; хранение и передача секрета, если он вообще потребуется, требуют отдельного решения.
7. После перезапуска успешная запись восстанавливает собственные структуры обоих модулей без интерпретации их физики общим хранилищем; повреждённый или несовместимый файл не уничтожает прежние данные.
8. Будущие тесты должны исполнить M01–M10 через Python и JSON CLI, проверить паритет ответов, конвертацию, конфликт ревизий, сериализацию обоих модулей, ошибки файлов и ограничения раскрытия ответов. Случаи R04 проверяют математику, а не эксперимент. Никакой из этих тестов в Д0 не запускался.

## 9. Первый кодовый этап и открытые решения

После отдельного утверждения контракта и задания на код предлагается **узкий headless-срез**: общая оболочка запросов/диагностик, сеанс и ревизии, два маленьких учебных сценария для качественного выбора и условного снимка, справка по ID, запись/восстановление JSON и тесты Python/CLI. Второй сценарий может использовать только проверочное условное значение/зафиксированный эталон как тестовую фикстуру: не выдавать фикстуру за физическую модель и не внедрять расчёт ε–NTU, реальные показания, GUI, диаграмму свойств, плагины, сервер или БД. Объём окончательно выбирается отдельным заданием; научные и методические блокеры сохраняются.

Открыты: Q17 — практическая проверка достаточности контракта двумя модулями, конкретные типы Python и совместимость версий; Q09/Q10 — доступ к ответам, критерии, внешний набор; Q11 — права на контент; Q15/Q16 — структура экспорта, путь, атомарность, миграции и восстановление; Q13 — упаковка. Нужно отдельно решить нормализацию единиц, права показа результатов в CLI, идемпотентность повторных команд, поведение параллельных экземпляров и область применения ревизий. Ни один из этих вопросов не закрывается бумажным примером.
