# Д2б: локальное конкурентное хранение

**Дата:** 28.10.2026. Код: `food_processes/storage.py`, `food_processes/core.py`; проверки: `tests/test_storage.py`. Это хранение в доверенном локальном каталоге, без сервера и БД. Физическая и методическая логика не изменялась.

## Обнаруженные риски и выбранная политика

В Д2а каждый процесс создавал `s1`, поэтому отдельные новые сеансы могли получить одинаковый ID и ошибочно выглядеть одним объектом при переносе или записи в общий файл. `os.replace` защищал от частичного файла при нормальной замене, но не различал двух авторов, прочитавших N и независимо получивших одинаковую ревизию N+1: последняя запись могла незаметно затереть первую. Сравнения численной ревизии недостаточно; простая проверка токена без блокировки оставляет гонку между проверкой и заменой.

Новые ID — `s-` и 32 шестнадцатеричных знака UUID4. Это практически маловероятная коллизия, не централизованная гарантия. Документы с прежними `s1`, `s2` и т. п. продолжают приниматься; восстановление сеанса с уже открытым ID возвращает `session.already_exists`, не заменяя данные. Независимо созданные старые сеансы с одинаковым ID невозможно автоматически различить: пользователь должен явно решить вопрос импорта. Файлы не переписываются ради обновления ID.

Выбраны **блокировка одного файла + оптимистический токен поколения**. `storage.read` и `storage.write` берут одну межпроцессную блокировку на целевое имя; на Windows используется `msvcrt.locking` по байту, на POSIX — `flock`. Внутри блокировки запись сверяет `expected_generation` с текущим токеном, затем записывает временный файл в том же каталоге, выполняет `flush`/`fsync` и `os.replace`. Каждая успешная запись получает новый случайный `g-…`, даже если содержимое осталось прежним. Поэтому две записи на основании одного токена не могут обе успешно заменить файл в штатно работающих экземплярах с этим протоколом. Отказ `storage.conflict` не повторяется автоматически. При конфликте клиент читает актуальный файл и явно решает, как объединить данные или сохранить свою копию под новым именем; простое повторение со свежим токеном без рассмотрения чужих данных не является слиянием.

Блокировка имеет ограниченное ожидание; при занятости возвращается `storage.lock_timeout`. Стабильный служебный файл `.<имя в нижнем регистре>.lock` не хранит сеанс и **не удаляется автоматически**: его повторное использование необходимо, чтобы два процесса не блокировали разные файловые объекты. ОС освобождает блокировку при завершении процесса; наличие файла само по себе не означает, что блокировка удерживается. Не удалять или подменять служебный файл, пока экземпляры приложения работают. Блокировка кооперативная: процессы, не использующие протокол, и пользователь с полным доступом к каталогу могут его обойти. На сетевых/синхронизируемых каталогах и с внешними синхронизаторами свойства не проверены; использовать личный локальный каталог.

Основания механизма: [Python `msvcrt.locking`](https://docs.python.org/3/library/msvcrt.html) и [Python `os.replace`](https://docs.python.org/3/library/os.html#os.replace). Документация `os.replace` отдельно указывает требование атомарности POSIX; для Windows ниже заявлены только фактически проверенные сценарии, а не универсальная гарантия любой файловой системы.

## Операции и формат

- `session.create` выдаёт новый UUID-ID; локальная ревизия по-прежнему проверяет изменения **внутри сеанса**, а не поколение файла.
- `session.save` создаёт документ в памяти. `storage.write` требует явное `expected_generation`: `null` только для создания отсутствующего файла; иначе — токен, полученный при чтении или предыдущей успешной записи. Отсутствующее поле даёт `storage.generation_required`; устаревший токен или неожиданное наличие/отсутствие файла — `storage.conflict`. При совпавшем токене и другом ID сеанса — `storage.session_mismatch`. Успешная запись возвращает новый `generation` и `saved_revision`.
- `storage.read` возвращает `{document, generation}`; `session.restore` принимает только документ. Токен относится к конкретному файлу и хранится клиентом отдельно от сеанса. Импорт документа в память и открытие существующего файла не разрешают перезапись: для неё нужен токен конкретного целевого файла. Для нового имени требуется `null`.
- Новый файл — обёртка `storage_format: food-processes-file`, `storage_version: 1`, `generation`, `document`. Документ внутри сохраняет прежние `format_version`, `module_data_version`, снимки и ответы. Для исходного JSON Д1/Д2а без обёртки `storage.read` вычисляет `legacy-` + SHA-256 фактических байтов; документ Д1 преобразуется только в памяти. Старый файл меняется лишь при явной записи с этим токеном. После записи он становится обёрткой; старые версии программы её не читают, поэтому обратная совместимость по записи не обещается. Исходный файл до явной записи остаётся нетронутым.
- Повреждённый, неизвестный или несовместимый документ отклоняется; запись не перезаписывает его. Если результат записи не удалось подтвердить, сначала читать файл и проверять поколение: ошибка после успешной замены потенциально означает, что запись уже состоялась. Это не автоматическое слияние.

Разрешены только имена ASCII вида `example.json` без путей; абсолютные пути, `../` и зарезервированные имена устройств Windows отклоняются. Тесты подтверждают запрет таких имён. Существующие символические ссылки целевого и служебного файла отклоняются проверкой кода; **фактический тест создания символической ссылки пропущен** из-за прав текущей Windows-среды. Защита от умышленной конкурентной подмены файла или каталога противником с полным доступом не заявлена.

## Проведённые испытания

28.10.2026, Windows, Python 3.11.9: `python -m pytest -q` — **52 passed, 1 skipped**. Пропуск: создание символической ссылки недоступно в текущей среде. Для реальной конкуренции использованы отдельные Python-процессы с управлением через stdin/stdout: оба открывают один документ и сигнализируют готовность до общей команды на запись. Получены одна успешная запись и один `storage.conflict`; проверены итоговый документ, одинаковая исходная ревизия, новый токен и восстановление победившей версии. Отдельные процессы выполняли 10 синхронизированных раундов чтения/записи: читатель получал согласованный документ и ревизию. Проверены 8 новых ID в отдельных процессах, тайм-аут занятой блокировки, её освобождение после принудительного завершения процесса, одинаковые данные с новым токеном, интеграция Python/CLI, ответы и история проверок, качественная точка и старые форматы Д1/Д2а.

Ошибки в тестах намеренно вызваны: до создания временного файла; во время частичной записи JSON; при `fsync`; после полного формирования временного файла перед заменой; при отказе `os.replace`; а также после фактической замены с имитацией потери подтверждения. При контролируемых ошибках до замены прежний файл сохранён, временные файлы удалены; после замены получен новый токен и повтор со старым токеном отклонён. Повреждённый JSON/обёртка и чужой сеанс не перезаписываются. Это программные имитации, а не реальные сбои питания.

При аварийном завершении во время записи временный файл может остаться; автоматическая очистка таких файлов не выполняется, поскольку другой процесс может ещё работать. После настоящего отключения питания или отказа устройства гарантии `fsync`/замены, восстановление каталога и файловой системы не испытаны. Символические ссылки, блокировки и атомарность на других файловых системах/сетевых ресурсах также не проверены.
