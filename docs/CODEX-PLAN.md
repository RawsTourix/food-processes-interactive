## Этап Д1 — узкий headless-срез контракта (выполнен, первый код)

**Статус:** выполнен узкий срез; фактические тесты, пропуск и ограничения приведены в [отчёте Д1](design/headless-d1.md). Q17 уточнён, но не закрыт. Постановка: исполнить основные гарантии [контракта Д0](design/application-api-contract.md) на двух разнородных модулях **без GUI и без физической симуляции**; выявленные изменения документа фиксировать вместе с проверками.

**Что сделать:**
- Минимальный чистый Python-пакет, доступный через импорт и JSON CLI с одинаковым поведением.
- Только нужный срез: диспетчер запросов/ответов, каталог двух модулей, сеанс и монотонная ревизия, команды, диагностики, ссылки на локальную справку, сериализация, безопасная запись/чтение JSON, восстановление.
- Два примера: (а) условный учебный сценарий теплообменника с конфигурацией, неизменяемым снимком и **тестовыми данными, явно помеченными как фикстура, а не рассчитанные показания**; (б) качественный выбор области/точки влажного воздуха без психрометрических свойств. Отказ запросов неподтверждённых модельных показаний обязателен.
- `pytest` проверяет атомарный отказ, конфликт ревизий, сохранность старого снимка, JSON round-trip обоих модулей, отказ записи с сохранением прежнего файла, отсутствие NaN/Infinity и недопустимой физики, паритет Python/CLI и отсутствие утечек скрытого эталона (если механизм проверки ответа входит в срез).
- Сохранения вне EXE, безопасный временный файл с последующей атомарной заменой; доступ к произвольному пути через CLI не делать по умолчанию. Неотработанные вопросы безопасности/совместимости пометить явно.

**Что не делать:** pywebview/HTML/JS, реальные теплофизические и психрометрические модели, насосы или полноценные лабораторные, графики, систему плагинов, сетевой сервер, БД и сложную общую абстракцию. Не считать выполненными M01–M10, если реально реализована только их часть.

**Критерий:** два headless-сценария действительно проходят в Python и JSON CLI, тесты запущены и результаты приведены; выявленные несоответствия Д0 отражены в документах, Q17 оценивается на основании фактического выполнения. Это **не** научная валидация теплообменника или готовое приложение.

## Этап Д2а — самостоятельные ответы, контекст проверки и политика показа (выполнен)

**Статус:** реализован срез без GUI, реальные тесты и ограничения — в [отчёте Д2а](design/headless-d2a.md). Q09/Q17 остаются открытыми. Опора: [фактический Д1](design/headless-d1.md), [контракт Д0](design/application-api-contract.md) и [методические правила](design/methodical-interaction.md).

**Цель:** добавить минимальные `answer.put` и `answer.check` в уже работающий API/CLI, не смешивая состояние ответа с происхождением данных и не создавая оценочную систему. Привязка к `snapshot_id`/версии, черновик, правило согласованности и возвращаемый статус проверки (`matches`, `does_not_match`, `not_checked`). Только **отдельное разрешённое тестовое задание** с фиксированным эталоном и допуском, явно отличное от открытой демонстрации R04. Для иных заданий без утверждённой проверки возвращать `not_checked` без выдуманных допусков.

**Политика доступа:** определить, через какие обычные операции студент видит ответ и справку, а через какие проверяет свою попытку. Не раскрывать эталон в публичной выдаче, сохранениях, диагностике, справке и JSON CLI до разрешённого действия. При этом зафиксировать ограничение: полностью офлайн-приложение с локальным кодом/данными **не обеспечивает криптографической секретности** эталонов от пользователя с доступом к файлам и отладке; это защита учебного сценария от случайного преждевременного раскрытия, не противодействие взлому.

**Проверки:** Python/JSON CLI, совпадение/несовпадение/непроверено, единицы, привязка к старому снимку при изменении условий, конфликт ревизий, отсутствие изменения при отказе, round-trip ответов и отсутствие случайного раскрытия эталона. Уточнить `show_fixture` как чтение либо явно документировать мутацию; согласовать `session.actions` с фактической доступностью команды. Предпочитать небольшие изменения и тесты, не широкую переработку.

**Выход:** код, работающие `pytest`, README и короткий отчёт; обновление Q09/Q17 по подтверждённым гарантиям. Не объявлять утверждёнными правила конкретного преподавателя и не реализовывать физику.

## Задание Г — технический spike pywebview/Windows (следующий этап, узкий GUI-прототип)

**Статус:** к выполнению отдельным заданием Codex; Д1/Д2а/Д2б завершены, результаты [Д2б](design/headless-d2b.md) подтверждены программными проверками. Г проверяет Q13 — техническую жизнеспособность **Windows x64 + pywebview + SVG + Python–JS bridge + упаковка**, независимо от научной готовности модели стенда.

**Разрешённый объём:** изолированный мини-прототип с одним окном и простой SVG-схемой, взаимодействием JS → существующий `Application.request` → JS; по одной наглядной операции для двух разнотипных модулей, вывод диагностик и возможность сохранения тестового сеанса через действующий storage API. GUI не содержит предметной физики и не выдаёт фикстуры R04/качественные точки за показания реального стенда. Не формировать полноценную лабораторную, весь интерфейс и дизайн-систему.

**Проверка среды:** реальный Windows запуск и закрытие, готовность `pywebviewready`, ответ Python–JS bridge, ошибки JS/bridge, Unicode/масштаб SVG, отсутствие HTTP-сервиса либо его локальность, доступ к статическим ресурсам из обычного и замороженного запуска. Отдельно проверить renderer EdgeChromium/WebView2 Runtime и .NET-предпосылки, а не считать их упакованными по умолчанию.

**Сборка:** пробные `onedir` и `onefile` PyInstaller (если окружение позволяет), воспроизводимые команды, размер и старт, положение ресурсов и сохранений вне временной папки EXE; проверка на Windows без установленного Python и без сети, когда доступна отдельная чистая среда. Если такая среда отсутствует — честно отметить непроверенное. Сравнить технические издержки и рекомендовать стек/формат поставки, не обещать «один EXE без системных зависимостей» до проверки.

**Выход:** `docs/design/windows-gui-spike.md`, небольшой изолированный код прототипа, тесты без окна там, где уместны, результаты реального ручного smoke-test, скрипты/спецификация сборки и уточнение Q13. Путь к EXE, размер и длительность запуска фиксировать только если измерены. Не публиковать большие сборочные файлы, частные данные и сторонние материалы в GitHub.

**После проверки Г:** отдельно принять решение о стекe, формате поставки, затем планировать постепенную разработку учебного UI поверх существующего API. Не переходить к физической модели или полному интерфейсу автоматически.

## Задание Е — первая лабораторная, UI и выпуск

После G2 реализовать физическую модель под тестами, затем интерфейс и материалы поверх Python API. Проверить полные сценарии прямотока/противотока, контекстную помощь, расчетные задания, сохранение, сравнение и самостоятельный вывод. Выполнить G3/G4, сборку и smoke-тест на совместимой Windows.

Новые лабораторные **реализуются** после проверки первого рабочего среза и их собственной методической базы. Но **краткий аудит** остальных и проверка границ общего API на сценарии диаграммы выполняются до фиксации архитектуры.

## Опционально: динамическая проверка оригинала

Запуск `Lab_FP.exe` только в изолированной Windows VM без сети и общих папок. Проверять **целевые UX-неопределённости** по подготовленному плану, а не повторять весь статический анализ. **VM не является обязательным входным условием для заданий А–Д**.

## Правила каждого следующего задания Codex

- Работать в текущем проекте и опираться на готовые отчёты; не повторять полный аудит и не пересказывать весь код Flash.
- Исходные PDFs, EXE, SWF, полный декомпилированный код остаются только на ноутбуке или во временных приватных каталогах. В публичный GitHub — собственная документация, ссылки на страницы, минимальные уместные свидетельства.
- Для каждого вывода различать: **установлено по исходнику / установлено по методике / независимая проверка / предположение / открытый вопрос**.
- После каждого задания: изменённые файлы, проверенные источники, фактически проведённые тесты, результаты, ограничения и предложенное следующее решение.
- Не переходить к программированию, скачиванию новых инструментов и следующим фазам по собственной инициативе, если задача определена как аналитическая.
